## Executive Summary

This document defines the data requirements for the Patient 360 Search initiative. The goal is to consolidate patient data from the Synthea healthcare database into a unified search interface, enabling clinicians and staff to retrieve a complete patient profile in under 2 seconds. The solution will reduce pre-appointment chart review time by 50%, eliminate missed allergy alerts, and support approximately 400 concurrent users during peak hours. This DRD covers source system discovery, data quality expectations, consumer requirements, and business rules for the data foundation phase (Phase 1).

---

## 1. Business Context

### 1.1 Business Request

Clinicians currently navigate three to five separate systems to piece together a complete picture of a patient before each appointment. On average, a physician spends 8 minutes per patient finding and cross-referencing information across systems. This fragmented workflow creates clinician frustration, risks missing critical information (allergies, recent lab results), prevents care coordinators from efficiently identifying care gaps, and causes billing staff to spend excessive time reconciling encounter and claims data.

The desired outcome is a **Patient 360 experience** — a single search interface where any authorized staff member can type a patient's name and instantly see a consolidated view including demographics, recent encounters, active diagnoses, current medications, lab results, allergies, and billing summary.

### 1.2 Business Objectives

- Reduce clinician time spent on patient lookups from 8 minutes to under 30 seconds
- Eliminate missed allergy alerts by surfacing them prominently in every search result
- Enable care coordinators to review 30+ patients per day (up from 10-15 currently)
- Provide billing staff with instant access to encounter-claims reconciliation
- Support quality reporting by making readmission data easily accessible

### 1.3 Success Criteria

- 90% of searches return complete results within 2 seconds
- Clinician satisfaction score above 4.0 out of 5.0 in post-launch survey
- 50% reduction in pre-appointment chart review time
- Zero missed allergy alerts in the first 90 days
- All active patients (~5,767 in current system) searchable from day one

## 5. Business Rules

### 5.1 Default Values

| Field | Default Value | When Applied | Business Justification |
|-------|---------------|--------------|------------------------|
| Patient age | Calculate from birthdate | When age is displayed in UI | Age must always be current; never store static age |
| Medication status | 'Active' | When stop date is NULL or > current date | Clinicians need to know what patient is currently taking |
| Condition status | 'Active' | When stop date is NULL or > current date | Active conditions drive treatment decisions |
| Allergy severity | 'Unknown' | When severity1 is NULL | Conservative approach - alert clinician to verify |
| Encounter cost | 0.00 | When total_claim_cost is NULL | Avoid NULL in financial calculations |

### 5.2 Calculations and Derivations

#### Patient Age

- **Formula / Logic**: `FLOOR(DATEDIFF(day, birthdate, CURRENT_DATE) / 365.25)`
- **Input Fields**: patients.birthdate, current system date
- **Output Field**: calculated_age (integer years)
- **Business Purpose**: Display patient age in search results and profile for clinical context
- **Example**: birthdate = '1980-06-15', current date = '2026-02-01' -> age = 45

#### Active Medication List

- **Formula / Logic**: `WHERE stop IS NULL OR stop > CURRENT_DATE`
- **Input Fields**: medications.start, medications.stop
- **Output Field**: is_active (boolean)
- **Business Purpose**: Distinguish current medications from historical for clinical safety
- **Example**: start = '2025-01-01', stop = NULL -> is_active = true

#### Active Condition List

- **Formula / Logic**: `WHERE stop IS NULL OR stop > CURRENT_DATE`
- **Input Fields**: conditions.start, conditions.stop
- **Output Field**: is_active (boolean)
- **Business Purpose**: Show current diagnoses vs. resolved conditions
- **Example**: start = '2024-03-01', stop = '2024-06-30' -> is_active = false

#### 30-Day Readmission Flag

- **Formula / Logic**: Inpatient encounter within 30 days of previous inpatient discharge
- **Input Fields**: encounters.start, encounters.stop, encounters.encounterclass
- **Output Field**: is_readmission (boolean)
- **Business Purpose**: Quality reporting; identifies patients needing post-discharge follow-up
- **Example**: Discharge on 2026-01-01, new inpatient admit on 2026-01-20 -> is_readmission = true

#### Total Visit Cost

- **Formula / Logic**: `encounter.base_encounter_cost + SUM(procedures.base_cost) + SUM(medications.base_cost)`
- **Input Fields**: encounters.base_encounter_cost, procedures.base_cost, medications.base_cost
- **Output Field**: total_visit_cost (decimal)
- **Business Purpose**: Billing staff need pre-calculated cost per encounter for reconciliation
- **Example**: Encounter cost $100 + 2 procedures at $50 each + medication $25 = $225 total

### 5.3 Transformation Rules

- **Patient name formatting**: Display as "Last, First" in search results; "First Last" in profile header
- **Date formatting**: Display all dates in MM/DD/YYYY format for US clinical users
- **SSN masking**: Display only last 4 digits (XXX-XX-1234) for patient disambiguation
- **Phone formatting**: Display as (XXX) XXX-XXXX
- **Cost formatting**: Display with 2 decimal places and dollar sign ($1,234.56)
- **Medication description**: Preserve full description including dosage from source system

### 5.4 Edge Cases and Exceptions

- **Scenario**: Patient has multiple insurance payers (primary and secondary)
  - **Expected Behavior**: Display both payers in financial profile; use primary payer for cost coverage calculations
  - **Rationale**: Billing staff confirmed they need visibility into both payers for claims reconciliation

- **Scenario**: Patient has common name with multiple matches (e.g., "John Smith")
  - **Expected Behavior**: Display date of birth and last 4 of SSN in search results to help user select correct patient
  - **Rationale**: End-user feedback from Dr. Nguyen; prevents selecting wrong patient

- **Scenario**: Patient has allergies with NULL severity
  - **Expected Behavior**: Display allergy prominently with severity shown as "Unknown"
  - **Rationale**: Patient safety requires displaying all allergies; conservative approach when severity unknown

- **Scenario**: Encounter has NULL stop timestamp
  - **Expected Behavior**: Display as ongoing encounter; do not calculate duration
  - **Rationale**: Some encounter types (ongoing care) may not have explicit end times

- **Scenario**: Deceased patient (deathdate is not NULL)
  - **Expected Behavior**: Display deceased indicator prominently; still allow full profile access for billing/records
  - **Rationale**: Clinicians should not attempt to schedule deceased patients; billing may still need access

## 6. Assumptions and Open Questions

### 6.1 Assumptions

- All patient data resides in the single Synthea DuckDB database; no additional source systems need integration in Phase 1
- The existing DuckDB infrastructure can support 400+ concurrent read queries with sub-2-second response times
- Data is loaded via daily batch ETL from CSV source files; hourly incremental loading can be implemented for clinical tables if needed
- HIPAA compliance architecture will be addressed in a separate security workstream and is not blocking Phase 1 data consolidation
- Role-based access control (RBAC) is deferred to Phase 2; Phase 1 assumes all authenticated users can access all patient data
- No data masking or de-identification is required for Phase 1 (internal clinical use only)
