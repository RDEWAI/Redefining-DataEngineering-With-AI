## Session continuation — update-stories for STORY-03-001 source dedup (v1.15)

### Trigger
2026-05-23 DAG re-run (`manual_ld_20260523T222531Z`) reproduced a SCD2 anti-pattern
bug: `DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE` on the second silver
run.

### Root cause
- Bronze `synthea_patients` accumulates one snapshot per `ds` partition; the same
  `patient_id` appears in every snapshot.
- `transform_patients.py` reads bronze across all partitions (~80k rows for ~6k
  distinct patients) and passes that DataFrame to `apply_scd2` without dedup.
- `apply_scd2`'s MERGE rejects multiple source rows hitting the same target.
- First-ever run masks the bug — cold-warehouse branch uses
  `.write.format("delta").mode("overwrite").save(target_path)` (no MERGE, accepts
  duplicates). Every subsequent run hits MERGE and fails.
- `apply_scd2` itself is correct — DMS §6 + LLD v1.18 §2.3 specify the caller
  is responsible for deduping before MERGE.

### Update scenario
Scenario C (same v1, same date 2026-05-23). v1.14 → v1.15, edit in-place.

### Changes applied
- `outputs/stories/v1/EPIC-03-silver-dimensions/STORY-03-001-silver-dim-patients.md`:
  - **Added AC11** — source DataFrame MUST be deduped to one row per natural
    key (`patient_id`) BEFORE `apply_scd2`. Recommended pattern:
    `row_number() OVER (PARTITION BY patient_id ORDER BY ds DESC) == 1`;
    fallback ordering by `_ingested_at` when `ds` missing.
  - Verification block extended (AC11): `file_exists` `transform_patients.py`;
