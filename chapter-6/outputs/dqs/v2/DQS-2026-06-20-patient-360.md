## 1. Overview

This Data Quality Specification defines validation rules, statistical baselines, reconciliation checks, and alert/escalation frameworks for the Patient 360 Medallion Pipeline. The pipeline ingests 13 Synthea Healthcare EHR source tables through Bronze (raw copy), Silver (canonical business entities with SCD Type 2), and Gold (denormalized consumer tables) layers. Rules cover 5,767 patients, 340,532 encounters, 4,366,447 observations, and 10 additional clinical/reference tables.

All rules are designed for execution via **spark-expectations >= 2.6.0** and enforce the zero-missed-allergy requirement [DRD SS1.3], the 2-second search SLA [DRD SS4.3], and HIPAA PHI handling requirements [DRD SS7].

**v2.0 Updates**: Aligned with STM v2.0 and DMS v1.1 changes -- added ARRAY<STRUCT> complex type validations (cardinality bounds, nested field NOT NULL, cross-field consistency), financial column negative value rejection (CRITICAL), full Gold column coverage for all new columns including LOW criticality optional fields, and SCD2 mid-batch / consumer overwrite failure edge case rules.

**v2.1 Updates**: DQ-FLD-078 (clinical_observations.encounter_id NOT NULL) changed from Reject/CRITICAL to Drop/WARNING. Synthea observations legitimately occur without an encounter (standalone lab / patient-reported results -- ~159K of 4.37M source rows, 3.6%, have a NULL encounter), and the Silver model keys observations by encounter, so these rows are out-of-scope rather than errors. Spark-Expectations now filters (drops) these rows before the Silver write (action=drop on source DQ) in all environments, with a drop alert if the dropped fraction exceeds 5%. The identical encounter_id NOT NULL rules on conditions, medications, procedures, immunizations, and encounters are unchanged (their source data has no NULL encounters).

**v2.2 Updates**: Infrastructure alignment with LLD §13 Decision 12 (corrected 2026-06-20) for **Unity Catalog OSS 0.5.0**. No DQ rule logic, severity, threshold, or baseline changed -- this update is naming-convention and audit-sink only. (1) **Fully-qualified table names (FQN)**: every table reference in this DQS now uses the three-part `unity.<schema>.<table>` form (catalog `unity`, with `spark.sql.defaultCatalog=unity`), replacing the prior two-part `<schema>.<table>` form, to match how Spark-Expectations and the reconciliation tasks address tables at runtime. (2) **Managed SE error/stats audit tables re-enabled**: Spark-Expectations now writes per-table `_error` and `_stats` audit tables as **MANAGED Unity Catalog tables** addressed by a per-table 3-part FQN (`unity.<schema>.<table>_error` / `unity.<schema>.<table>_stats`), created by SE via `saveAsTable` on first run; `se.enable.error.table` and `se.enable.stats.table` stay `True`. The MANAGED `<table>_error` table is now the **primary rejected-row audit trail** for all `Reject + Quarantine` and `Reject record` actions; the legacy filesystem `quarantine_path` becomes an optional secondary sink. Business Bronze/Silver/Gold tables remain EXTERNAL Delta (pre-created by Liquibase); only the SE audit tables are MANAGED. See the new design decision "SE Audit-Table Sink Strategy (v2.2)" below.

### Severity Definitions

| Severity | Action | Response Time | Description |
|----------|--------|---------------|-------------|
| **CRITICAL** | Halt pipeline or reject record | 15 minutes | Data integrity risk that propagates to consumers and causes incorrect clinical/business decisions. Examples: NULL PK, broken FK in fact table, row count drop >5%, allergy data failure, negative financial values. |
| **WARNING** | Log and continue / quarantine row | 4 hours | Degrades data quality but does not corrupt downstream analytics. Examples: unexpected enum value, elevated null rate within tolerance, out-of-range date, ARRAY<STRUCT> cardinality exceeding bounds. |
| **INFO** | Record for monitoring only | Next business day | Observational checks for trend tracking. Examples: slowly increasing null rates, new categorical values, minor row count variation. |

### Key Design Decisions

#### Decision: FK Orphan Handling Strategy

**Options Considered**:
1. Reject only -- halt pipeline on orphan records, no quarantine
2. Reject + Quarantine -- reject orphan records to a quarantine table, log details, continue pipeline for non-orphan records
3. Default SK -- assign a default surrogate key (-1) for missing parents

**Selected**: Option 2 (Reject + Quarantine)

**Rationale**: Aligns with the STM Edge Cases sheet (DQ-021, DQ-022) which specifies "REJECT record to quarantine table; log warning with encounter_id and patient_id; do not load to Gold." Healthcare data requires traceability of rejected records for compliance audits [DRD SS7.5]. Quarantine enables investigation without blocking the entire pipeline for non-orphan records.

**Trade-off**: Requires quarantine table schema definition (due 2026-04-01). Slightly more complex than reject-only, but necessary for HIPAA audit trail requirements.

#### Decision: Statistical Distribution Thresholds

**Options Considered**:
1. Tight thresholds (+/-2%) for all tables -- maximum anomaly detection sensitivity
2. Enterprise defaults (+/-5% fact, +/-2% dimension) -- standard tolerance
3. Hybrid -- tight thresholds (+/-2%) for patient-critical tables, enterprise defaults (+/-5%) for the rest

**Selected**: Option 3 (Hybrid)

**Rationale**: Patient-critical tables (patients, encounters, allergies) directly feed the Clinical Dashboard with a 1-hour SLA [DRD SS4.4] and the zero-missed-allergy requirement [DRD SS1.3]. Tight thresholds on these tables provide earlier anomaly detection where patient safety is at stake. Enterprise defaults for reference and supporting tables (organizations, providers, payers, careplans) avoid alert fatigue from tables with naturally stable or slowly-changing volumes.

**Trade-off**: Two threshold tiers add configuration complexity. Acceptable because the patient-safety benefit outweighs the marginal operational overhead.

#### Decision: Allergy DQ Failure Escalation Path

**Options Considered**:
1. Standard CRITICAL path -- PagerDuty to on-call engineer, 15-minute response
2. Elevated path -- PagerDuty to on-call engineer AND Clinical Ops Director, 10-minute response target

**Selected**: Option 2 (Elevated Path)

**Rationale**: The DRD specifies "zero missed allergy alerts in the first 90 days" [DRD SS1.3] and classifies allergies as "PHI - Clinical (Safety Critical)" [DRD SS7.2]. A missed allergy in the Clinical Dashboard could lead to a patient safety incident. The elevated escalation ensures both the technical team and the clinical stakeholder responsible for patient safety are immediately aware. The 10-minute response target (vs standard 15 minutes) reflects the safety-critical nature of allergy data.

**Trade-off**: Higher alert volume for clinical operations leadership. Acceptable given the zero-tolerance allergy requirement and the 90-day post-launch safety window.

#### Decision: ARRAY<STRUCT> Validation Depth (v2.0)

**Options Considered**:
1. Shallow validation -- only check that column is non-null or array is present
2. Cardinality-only -- check upper cardinality bounds but not nested field values
3. Full validation -- cardinality bounds + NOT NULL on nested struct fields + cross-field consistency (e.g., verify array is non-empty when has_allergy=TRUE)

**Selected**: Option 3 (Full validation)

**Rationale**: The ARRAY<STRUCT> columns (allergies, conditions, medications) in patient_summary are safety-critical for allergy data [DRD SS1.3] and directly displayed in the Clinical Dashboard. Shallow or cardinality-only validation would miss nested NULL descriptions or empty arrays when has_allergy=TRUE, both of which would cause incorrect clinical display. Full validation ensures cross-field consistency between scalar flags and array contents.

**Trade-off**: Higher rule count and more complex query_dq expressions. Acceptable because patient safety requires complete array content validation, and these are Gold-layer checks that run after upstream Silver rules have already filtered most defects.

#### Decision: Financial Column Negative Value Severity (v2.0)

**Options Considered**:
1. WARNING -- flag and continue, allow negative values through
2. CRITICAL -- reject records with negative healthcare_expenses, healthcare_coverage, or income values

**Selected**: Option 2 (CRITICAL -- reject)

**Rationale**: Negative financial values (healthcare_expenses, healthcare_coverage, income) in clinical_patients indicate upstream data corruption since these represent cumulative lifetime values that should never be negative in Synthea source data. The SCD2 hash now includes these columns [DMS SS6, STM v2.0], so corrupted financial values would trigger unnecessary SCD2 version creation and pollute patient history. Rejecting at Silver prevents cascade into Gold aggregations.

**Trade-off**: Rejected records reduce Silver completeness. Acceptable because negative lifetime financial values are definitionally invalid in this domain and should trigger source investigation.

#### Decision: SCD2 Mid-Batch and Consumer Table Failure Handling (v2.0)

**Options Considered**:
1. Monitor only -- log warnings for SCD2 mid-batch changes and overwrite failures
2. Full DQ coverage -- add validation rules for SCD2 mid-batch atomicity (DQ-053/054/055) and overwrite failure detection (DQ-056)

**Selected**: Option 2 (Full DQ coverage)

**Rationale**: STM v2.0 Edge Cases DQ-053 through DQ-056 define specific handling for reference SCD2 mid-batch changes and consumer table overwrite failures. Without DQ rules monitoring these scenarios, mid-batch SCD2 version conflicts would go undetected, and consumer table corruption from failed overwrites could serve stale or incomplete data to the Clinical Dashboard [DRD SS4.4].

**Trade-off**: Additional monitoring overhead for relatively rare events. Acceptable because the impact of undetected failure in these scenarios is high (stale clinical data or corrupted consumer tables).

#### Decision: SE Audit-Table Sink Strategy (v2.2)

**Options Considered**:
1. Path-based SE audit tables -- write SE `_error`/`_stats` to a filesystem path (`warehouse/{env}/_se/<table>/`) via `.option("path", ...)`; keep a separate filesystem `quarantine_path` as the rejected-row audit trail
2. MANAGED FQN SE audit tables -- write SE `_error`/`_stats` as MANAGED Unity Catalog tables addressed by a per-table 3-part FQN (`unity.<schema>.<table>_error` / `_stats`), created by SE via `saveAsTable`; the `_error` table becomes the primary rejected-row audit trail and `quarantine_path` becomes an optional secondary sink

**Selected**: Option 2 (MANAGED FQN SE audit tables)

**Rationale**: Unity Catalog OSS 0.5.0 fixes the empty-namespace defect that previously crashed bare-name SE audit-table creates under spark-submit (length-0 namespace -> `ArrayIndexOutOfBoundsException`) and adds support for managed `saveAsTable` creates [LLD §13 Decision 12, corrected 2026-06-20]. Passing the FQN `target_table` makes SE's derived `<target>_error` / `<target>_stats` names well-formed 3-part identifiers, so the managed writes succeed. A MANAGED, catalog-registered `_error` table is queryable through the catalog, governed by UC, and carries the full per-table source schema -- a stronger HIPAA audit trail [DRD SS7.5] than opaque filesystem files. Per-table FQN derivation also prevents the `DELTA_*` schema-merge collision that a single shared `bronze_se_error` name would cause across tables with different schemas. `se.enable.error.table` and `se.enable.stats.table` stay `True`.

**Trade-off**: MANAGED tables are SE-owned (created on first run, not pre-created by Liquibase), so they are absent until the first pipeline execution and must NOT be added to the Liquibase changelog. Acceptable: the SE library owns their lifecycle, and business Bronze/Silver/Gold tables remain EXTERNAL Delta (Decision 15) -- only the audit tables are MANAGED.

## 3. Referential Integrity Rules

All FK violations are handled by **Reject + Quarantine**: the orphan record is rejected and captured with full logging (child key, parent key, timestamp, batch ID), and the pipeline continues for valid records. This aligns with STM Edge Cases sheet (DQ-021, DQ-022) and HIPAA audit requirements [DRD SS7.5].

**Audit sink (v2.2)**: Rejected/quarantined rows land in the **MANAGED Spark-Expectations `_error` table** for the relevant business table -- `unity.<schema>.<table>_error` (e.g. orphan `clinical_encounters` rows -> `unity.clinical.clinical_encounters_error`), created by SE via `saveAsTable` on UC 0.5.0. This catalog-registered, UC-governed table is the **primary** rejected-row audit trail. The legacy filesystem `quarantine_path` is retained as an optional secondary sink. See the "SE Audit-Table Sink Strategy (v2.2)" decision in Section 1.

**Exception**: Gold-layer fact tables use a fallback to current SCD2 version (`is_current=TRUE`) when no matching effective date range exists [STM Edge Case DQ-023], logged as WARNING.
